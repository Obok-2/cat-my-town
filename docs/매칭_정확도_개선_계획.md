# 매칭 정확도 개선 계획

같은 고양이를 다시 찍었을 때 올바른 고양이가 후보로 나오고, 다른 고양이는 후보에 오르지 않도록
동일 개체 판별 정확도를 높이기 위한 계획이다. 앱·관리자 웹·API 응답 형식은 바꾸지 않는다.

---

## 1. 지금 구조와 문제

```
촬영 사진(전체) → DJL ResNet-18(고양이 판별) → Voyage AI 임베딩(사진 전체) → pgvector 검색 → 후보
```

- **사진 전체를 임베딩한다.** 범용 임베딩(Voyage)은 고양이만이 아니라 배경·구도까지 반영해서,
  배경이 비슷하면 다른 고양이도 유사도가 높게 나온다.
- **색·무늬가 비슷한 다른 고양이를 구분하기 어렵다.** 실제 테스트에서 흰색+회색 무늬 고양이와
  털이 긴 고등어·삼색 고양이가 일치율 46~52%로 후보에 올랐다(기준 40% 초과).
- 판별 모델(ResNet-18)은 고양이가 작게 찍히거나 가려지면 놓치기 쉽다.

## 2. 목표 구조

```
앱 → Spring 서버 ──→ vision 서버(FastAPI, Python)
                      ├ YOLO-seg: 고양이 찾기 → 윤곽만 남기고 배경 제거
                      └ (2단계) 개체 식별용 임베딩 생성
                   ←── 판별 결과 + 배경 제거 이미지(또는 임베딩)
     Spring → pgvector 검색 → 후보
```

- 모델은 **이미 학습된 공개 모델을 그대로 가져다 쓴다**(학습·파인튜닝 없음).
- 원본 사진은 지금처럼 MinIO에 저장하고 앱에는 원본을 보여준다.
  **배경 제거 이미지는 임베딩을 만드는 동안만 쓰고 저장하지 않는다.**

### 최종 목표 (2단계까지 적용한 모습)

```
앱 → Spring 서버 ──사진──→ vision 서버(FastAPI, 컨테이너 1개)
                            ├ YOLO11-seg     : 고양이 찾기 + 배경 제거
                            └ MegaDescriptor : 배경 제거 이미지 → 임베딩
                  ←── { isCat, confidence, box, embedding }
     Spring → pgvector 검색(+ 위치 가중치) → 후보 → 사용자가 최종 확인
```

- **Voyage AI 호출이 없어진다.** 사진 한 번 보내면 vision 서버 안에서 "오리기 → 임베딩"을 이어서 처리한다.
- **MegaDescriptor는 서버를 따로 두지 않고 vision 서버 안에 같이 둔다.**
  둘 다 Python·PyTorch라 같은 환경에 들어가고, 사진을 한 번만 주고받으며, 관리할 컨테이너가 늘지 않는다.
  사용량이 크게 늘어 한 서버로 버거워지면 그때 나눈다.

## 2-1. 모델 선택

| 모델 | 하는 일 | 비유 | 가격·라이선스 |
|---|---|---|---|
| **YOLO11-seg** | 사진에서 고양이 **위치를 찾고 윤곽대로 오림**, 고양이 여부 판별 | 가위질하는 사람 | 무료 · AGPL-3.0 |
| **MegaDescriptor** (채택) | 오린 고양이를 **숫자 목록(임베딩)**으로 바꿈. "같은 동물 개체인지" 구분하도록 학습된 모델 | 개체 구분을 공부한 카드 작성자 | 무료 · 비상업 라이선스로 알려짐(포트폴리오·무료 앱은 사용 가능) |
| DINOv2 (예비) | 임베딩. 사진만으로 학습해 무늬·질감 같은 세부 모양에 강함 | 세부 모양을 잘 보는 카드 작성자 | 무료 · Apache 2.0(상업 사용 가능) |
| Voyage (제거 예정) | 임베딩. 사진↔글 짝을 학습해 "무슨 사진인지"(종류·상황)에 강함 | 말로 설명하는 카드 작성자 | 유료 API · 사진이 외부로 전송됨 |

**MegaDescriptor를 고른 이유**
- 문제가 "비슷한 무늬의 **다른** 고양이를 같다고 판단"하는 것인데, Voyage는 둘 다 "삼색 고양이"로 보고 가깝게 만든다.
  MegaDescriptor는 같은 개체는 가깝게, 다른 개체는 멀게 되도록 학습돼 이 문제에 가장 잘 맞는다.
- 우리 서버에서 돌아서 **Voyage 요금이 없고 사진이 외부로 나가지 않는다.**

**예비안으로 바꾸는 경우**
- 백엔드 서버에서 사진 한 장 처리가 너무 느리면(2~3초 이상): MegaDescriptor 작은 버전 또는 DINOv2
- 돈을 받는 서비스로 전환하면: DINOv2(상업 사용 가능). 이때 YOLO도 라이선스를 다시 검토한다(8절).

## 4. 1단계 작업 목록 (배경 제거)

### 4-1. 새로 만드는 것: `vision/` (Python FastAPI)
- `POST /analyze`: 사진 1장을 받아 결과를 돌려준다.
  - 고양이 없음: `{ "isCat": false, "label": "...", "confidence": 0.0 }`
  - 고양이 있음: `{ "isCat": true, "confidence": 0.93, "box": { "x": 0.21, "y": 0.34, "w": 0.40, "h": 0.52 }, "image": "<배경 제거 JPEG, base64>" }`
  - 고양이가 여러 마리면 **확률 × 면적**이 가장 큰 한 마리를 고른다.
- 모델: Ultralytics YOLO-seg 가장 작은 모델(예: `yolo11n-seg.pt`), 서버 시작 시 한 번 불러 둔다.
- 배경 처리: 마스크 밖을 중간 회색(또는 흰색)으로 채우고, 고양이 네모 영역으로 잘라 여백을 약간 둔다.
- Dockerfile: ARM64 서버용, CPU 버전 PyTorch.
- **상태: 완료(`vision/`).** 로컬(Windows, CPU)에서 확인한 결과
  - 삼색 고양이(흰 벽·시멘트 바닥): 고양이 판별 90.5%, 벽·바닥이 깔끔하게 제거됨, 처리 약 140ms(첫 요청은 모델 내려받기로 약 15초)
  - 치즈 고양이(베이지 방석 위): 판별 41.2%로 낮고, 털색과 비슷한 방석 일부가 윤곽에 같이 남음
    → 더 큰 모델(`yolo11s-seg`·`m-seg`, 환경변수만 변경)이나 마스크 가장자리 깎기로 개선 검토

### 4-2. 인프라
- `infra/docker-compose.yml`에 `vision` 컨테이너 추가. **외부 포트는 열지 않고** Spring만 `http://vision:8000`으로 호출한다.
- 모델 가중치는 호스트 폴더에 캐시해서 재시작 때 다시 받지 않는다.

### 4-3. Spring 서버 변경
| 파일 | 변경 |
|---|---|
| `CatImageClassifier.java` (DJL) | 삭제 → `VisionClient.java`(vision 서버 호출)로 대체 |
| `CameraService.java` | 판별 결과를 VisionClient에서 받고, 배경 제거 이미지를 Voyage로 보냄. `NOT_CAT` 판정 기준은 YOLO 확률로 변경 |
| `CatService.java` | 등록·목격 저장 시 박스 좌표·확률을 함께 저장(분석 때 만든 임베딩 재사용 흐름은 그대로) |
| `AnalysisEmbeddingStore.java` | 임베딩과 함께 박스 좌표·확률도 30분 보관 |
| `build.gradle` | DJL 의존성 3개 삭제(jar 경량화, Windows 로컬 실행 시 DLL 차단 문제도 해소) |
| `application.properties` | `vision.url=http://vision:8000` 추가, `camera.cat-detection.min-confidence`를 YOLO 기준으로 재정의 |

### 4-4. DB 변경 (`sightings`)
| 컬럼 | 타입 | 뜻 |
|---|---|---|
| `cat_box_x`, `cat_box_y`, `cat_box_w`, `cat_box_h` | NUMERIC(5, 4) | 고양이 위치 네모(사진 크기 대비 0~1 비율) |
| `cat_confidence` | NUMERIC(5, 4) | YOLO가 고양이라고 판단한 확률 |

- 저장 이유: 한 사진에 고양이가 여러 마리일 때 **나중에 임베딩을 다시 만들어도 같은 고양이를 고르기 위해**, 그리고 디버깅·기준값 튜닝용.
- 마스크(윤곽선) 자체는 크기가 커서 저장하지 않는다. 필요하면 원본에서 다시 계산한다.
- `schema.sql`과 ERD를 함께 고친다. 배포 DB에는 `ALTER TABLE sightings ADD COLUMN ...`으로 추가한다.

### 4-5. 기존 데이터 재처리
- 이미 등록된 목격 사진의 임베딩을 새 방식으로 **한 번 다시 만든다**:
  MinIO 원본 → vision `/analyze` → Voyage 임베딩 → `sightings.embedding`·박스 좌표 갱신.
- 원본 사진은 절대 지우지 않는다(방식이 바뀔 때마다 원본에서 다시 계산).

## 5. 2단계 작업 목록 (MegaDescriptor로 임베딩 교체)

### 5-1. vision 서버
- MegaDescriptor를 서버 시작 시 YOLO와 함께 불러 둔다(Hugging Face에서 `timm`으로 가져옴, 가중치는 `/models`에 캐시).
- `POST /analyze` 응답에 `embedding`(숫자 목록)을 추가한다. 배경 제거 이미지 → MegaDescriptor → 임베딩.
  비교·디버깅용으로 배경 제거 이미지(`image`)는 선택 옵션으로 남긴다.

### 5-2. Spring 서버
- `VoyageImageEmbeddingClient.java` 삭제 → vision 응답의 `embedding`을 그대로 사용.
- `application.properties`에서 `camera.voyage.*` 삭제(Voyage API 키 불필요).

### 5-3. DB — 임베딩 값이 완전히 달라진다
- 모델마다 **숫자 개수(차원)**와 **숫자의 뜻**이 달라서, Voyage로 만든 값과 MegaDescriptor로 만든 값은 **서로 비교할 수 없다.**
  (Voyage 1024개, MegaDescriptor 큰 버전 약 1536개, DINOv2 384~1536개)
- 그래서 전환 기간에는 **새 컬럼을 하나 더 두고 나란히 저장**한다.
  ```
  sightings.embedding      VECTOR(1024)   -- Voyage (기존)
  sightings.embedding_v2   VECTOR(새 차원) -- MegaDescriptor (추가, HNSW 인덱스 별도)
  ```
  - 같은 사진으로 두 모델 결과를 바로 비교할 수 있고, 결과가 나쁘면 새 컬럼만 지우면 되돌릴 수 있다.
  - 새 모델이 더 나으면 검색을 `embedding_v2`로 바꾸고, 안정되면 기존 컬럼을 지운다.
- 기존 목격 사진은 MinIO 원본 → vision → `embedding_v2`로 **한 번 다시 만든다.**
- 새 모델은 유사도 숫자 범위가 달라서 보정 기준값(0.75 / 0.92 / 40%)을 반드시 다시 정한다.

### 5-4. 문서·안내
- 개인정보 안내에서 "사진이 Voyage AI로 전송된다" 문구 삭제(사진이 외부로 나가지 않게 됨).
- README 기술 스택·시스템 구성도에서 Voyage를 MegaDescriptor로 바꾼다.

### 5-5. 진행 순서
1. 테스트 세트 준비(7절)
2. vision 서버에 MegaDescriptor 추가 → 사진 한 장 처리 시간 측정(너무 느리면 예비안)
3. **Voyage vs MegaDescriptor를 같은 테스트 세트로 비교**(Top-1·Top-3·오매칭률)
4. 더 좋은 쪽으로 교체 → 기존 사진 재변환 → 기준값 재조정
5. 위치 가중치 추가(6절)

## 6. 함께 검토할 개선 (모델 변경 없이)

- **위치 가중치:** 길고양이는 활동 반경이 좁다. 새 사진 위치와 기존 목격 위치가 가까울수록 점수를 더하고,
  멀리 떨어진 고양이는 감점·제외한다(모든 목격 기록에 좌표가 있으므로 SQL 계산만으로 가능).
- **후보 기준 상향:** 측정 결과에 따라 40%를 올려 애매한 후보를 줄인다.

## 7. 측정 방법

- **테스트 세트:** 고양이 10~20마리 × 각 3~5장(각도·장소를 조금씩 다르게). 직접 찍은 사진 또는 자유 이용 가능한 사진만 쓴다.
- **지표**
  - Top-1 정확도: 같은 고양이가 1순위 후보로 나온 비율
  - Top-3 정확도: 같은 고양이가 후보 3마리 안에 든 비율
  - 오매칭률: 다른 고양이가 기준(40%)을 넘어 후보에 오른 비율
  - 판별 실패율: 고양이 사진인데 `NOT_CAT`이 나온 비율
- **비교:** 지금 → 1단계 → (위치 가중치) → 2단계 순서로 같은 테스트 세트에서 측정해 표로 남긴다.
- 각 단계마다 유사도 분포를 보고 보정 기준값(`lower-bound`·`upper-bound`·`threshold`)을 다시 정한다.

## 8. 주의할 점

- **라이선스:** Ultralytics YOLO(v8·v11)는 AGPL-3.0. 공개 저장소·포트폴리오는 문제없지만,
  상업 서비스로 전환하면 소스 공개 의무 또는 유료 라이선스가 필요하다. 대안: RT-DETR, YOLOX(Apache 2.0).
- **라이선스(임베딩):** MegaDescriptor는 비상업 라이선스로 알려져 있다. 개인 포트폴리오·무료 앱은 문제없고,
  유료화하면 DINOv2(Apache 2.0)로 바꾼다. 사용 전 모델 페이지에서 조건을 다시 확인한다.
- **속도·메모리:** ARM CPU(2 OCPU·12GB)에서 YOLO-seg n 모델은 사진 한 장에 수백 ms 수준으로 예상(로컬 x86에서는 약 140ms).
  MegaDescriptor 큰 버전은 모델이 수백 MB~1GB라 메모리는 충분하지만, 한 장 처리가 1~2초까지 늘 수 있다(측정 필요).
- **한계:** 무늬가 거의 같은 고양이는 전용 모델로도 완벽히 구분하기 어렵다.
  "AI는 후보 제안, 확정은 사용자" 구조는 유지한다.
